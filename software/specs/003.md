## Purpose
This specification formalises a secure, reproducible, multi‑layer sandboxing strategy for development and AI‑driven automation on Ubuntu.  
It ensures that Python tools, agentic workflows, and experimental scripts execute within isolated, governed environments that protect the host system and maintain deterministic reproducibility.

## Objectives
- Define a layered isolation model for Ubuntu development  
- Formalise Python venv usage for application‑level isolation  
- Specify OS‑level sandboxing mechanisms (AppArmor, systemd, restricted users, chroot)  
- Define Docker containerization rules for full isolation  
- Establish integration patterns with local AI engineering stacks  
- Ensure deterministic, safe execution for agentic automation  

## Definitions
- **venv** — Python virtual environment providing isolated interpreter and dependencies.  
- **Restricted User** — Non‑privileged user with minimal permissions and no login shell.  
- **AppArmor** — Mandatory access control system restricting process capabilities.  
- **systemd Sandboxing** — Service‑level restrictions applied via systemd unit configuration.  
- **chroot** — Filesystem jail providing minimal environment isolation.  
- **Docker** — Container runtime providing full filesystem, network, and resource isolation.  
- **OpenCode** — Agent runtime executing tools inside sandboxed environments.  
- **Anything LLM** — Orchestration layer routing tasks and isolating RAG ingestion.  

## Requirements

### Functional Requirements
- Python environments must be isolated using venv.  
- High‑risk operations must run under restricted users or containers.  
- AppArmor profiles must restrict filesystem and network access.  
- systemd units must enforce privilege boundaries.  
- Docker containers must provide full isolation when required.  
- All sandboxing layers must operate offline.  

### Non‑Functional Requirements
- **Security**: No privileged execution unless explicitly authorised.  
- **Reproducibility**: Environments must be deterministic and rebuildable.  
- **Governance**: All agentic operations must be logged.  
- **Reliability**: File writes must be atomic.  
- **Performance**: Sandbox overhead must remain within acceptable bounds.

## Model / Scheme Description

### Layered Isolation Model
Sandboxing is implemented across three deterministic layers:

#### 1. Application‑Level Isolation
- Python venv  
- pip constraints  
- local dependencies  
- isolated interpreter  

#### 2. System‑Level Isolation
- restricted users  
- AppArmor profiles  
- systemd sandboxing  
- chroot environments  

#### 3. Container‑Level Isolation
- Docker  
- Podman  
- OCI containers  

Each layer can operate independently or be combined for maximum isolation.

### Component Relationships
- venv → isolates Python tools  
- restricted user → isolates process permissions  
- AppArmor → restricts filesystem + network  
- systemd → enforces runtime boundaries  
- chroot → isolates filesystem  
- Docker → isolates entire environment  
- OpenCode → executes tools inside any layer  
- Anything LLM → routes tasks to isolated environments  

### Constraints
- All sandboxing must remain local‑only.  
- No remote container execution.  
- No privileged Docker mode.  
- No uncontrolled filesystem access.

## Implementation Rules

### Python venv Rules
- One venv per project.  
- venv must not be committed to Git.  
- Dependencies must be frozen using `requirements.txt` or `pyproject.toml`.  
- AI agents must execute Python tools inside venv.

### Restricted User Rules
- Restricted users must have no login shell.  
- All high‑risk scripts must run under restricted users.  
- Agents may not escalate privileges.

### AppArmor Rules
Profiles must restrict:

- filesystem access  
- network access  
- execution capabilities  

Profiles must be generated using `aa-genprof` and enforced via `aa-enforce`.

### systemd Sandboxing Rules
Units must include:

- `ProtectSystem=full`  
- `ProtectHome=yes`  
- `PrivateTmp=yes`  
- `NoNewPrivileges=yes`  

### chroot Rules
- chroot environments must use minimal base systems.  
- Agents may not escape chroot.  
- chroot must be used for isolated builds or testing.

### Docker Rules
Containers must enforce:

- read‑only filesystem  
- no network  
- limited memory  
- limited CPU  
- no privileged mode  

Dockerfiles must define deterministic build steps.

### Integration Rules
OpenCode must be able to execute tools inside:

- venv  
- restricted user  
- chroot  
- Docker container  

Anything LLM must route tasks to isolated environments based on risk level.

## Exceptions & Edge Cases
- **GPU Access** — Docker containers may require explicit device mapping.  
- **Large Models** — llama.cpp may require increased memory limits.  
- **Network‑Dependent Tools** — Must be explicitly authorised.  
- **Legacy Python Tools** — May require system Python; must be isolated via Docker.
