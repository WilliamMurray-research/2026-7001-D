## Purpose
This specification formalises the architecture and operational patterns required for AI agents to interact with local Git repositories and optionally maintain documentation within Obsidian.  
It ensures deterministic, safe, version‑controlled agentic operations across codebases and knowledge vaults, enabling unified project reasoning, documentation generation, and RAG‑powered retrieval.

## Objectives
- Define the components required for local Git integration  
- Specify deterministic Git‑aware agent workflows  
- Formalise optional Obsidian vault integration  
- Establish rules for documentation generation and versioning  
- Define RAG ingestion patterns for Git + Obsidian  
- Ensure local‑only, privacy‑preserving operation  

## Definitions
- **Local Git Repository** — The authoritative source of truth for code and documentation.  
- **OpenCode** — Agent runtime performing Git operations, reasoning, patch generation, and file writes.  
- **Anything LLM** — Orchestration layer providing routing, RAG ingestion, and workflow triggers.  
- **Obsidian Vault** — Optional markdown‑based knowledge base stored locally and version‑controlled.  
- **llama.cpp** — Lightweight inference runtime for fast conversational queries.  
- **Unsloth Desktop** — Fine‑tuning engine for project‑specific model specialisation.  
- **Git Tools** — Deterministic functions exposed to OpenCode for interacting with Git.  
- **RAG** — Retrieval‑augmented generation using ingested repository and vault content.

## Requirements

### Functional Requirements
- Agents must execute Git commands deterministically through sandboxed tools.  
- Agents must generate structured patches and apply them safely.  
- Documentation updates must be written as markdown files.  
- Git commits must be atomic and include structured commit messages.  
- Optional Obsidian vault integration must support bidirectional updates.  
- RAG ingestion must support both code and documentation.

### Non‑Functional Requirements
- **Performance**: Git operations must complete within deterministic bounds.  
- **Reliability**: Patch application must use atomic writes.  
- **Governance**: All Git commands and file modifications must be logged.  
- **Security**: No remote Git operations unless explicitly authorised.  
- **Compliance**: All commits must pass validation checks.

## Model / Scheme Description

### Components
- **Git Repository** — Provides version control, diffs, commit history, and branching.  
- **OpenCode** — Executes Git tools, generates patches, manages project sessions.  
- **Anything LLM** — Routes tasks, triggers workflows, ingests repositories and vaults.  
- **Obsidian** — Optional documentation and knowledge layer.  
- **llama.cpp** — Provides fast inference for lightweight queries.  
- **Unsloth Desktop** — Produces fine‑tuned models for project‑specific reasoning.

### Relationships
- Anything LLM → routes → OpenCode  
- OpenCode → executes → Git tools  
- OpenCode → writes → documentation into Obsidian vault  
- Anything LLM → ingests → Git repository + Obsidian vault  
- RAG → provides → contextual retrieval for agent reasoning  

### Constraints
- All components must operate offline.  
- Git operations must be executed only through approved tools.  
- Obsidian vault must be stored inside the Git repository if used.

## Implementation Rules

### Naming Rules
- Git tools must follow snake_case naming.  
- Commit messages must follow a structured format (deterministic prefix + summary).

### Directory Rules
Recommended structure:

```
project/
  src/
  docs/
  vault/   # optional Obsidian vault
```

### Git Tool Definitions
OpenCode must expose:

- `git_status()`  
- `git_diff(path)`  
- `gitapplypatch(diff)`  
- `git_commit(message)`  
- `git_checkout(branch)`  
- `gitcreatebranch(name)`  
- `git_log()`  

### Documentation Rules
- Documentation must be written in markdown.  
- Obsidian vault notes must follow deterministic naming conventions.  
- AI‑generated documentation must be committed alongside code.

### Validation Rules
- All patches must be validated before commit.  
- All documentation updates must pass markdown linting.  
- All Git operations must be logged.

### Manifest Integration Rules
- Repository root must be registered in the project session.  
- RAG ingestion must record file hashes for consistency.

## Compliance & Verification

### Automated Checks
- Patch validation  
- Commit message structure  
- Markdown linting  
- Branch integrity  
- Syntax correctness  

### Manual Review
- Reasoning trace inspection  
- Documentation quality  
- Commit history review  

### Required Artefacts
- Change summary  
- Commit details  
- Modified file list  
- Execution logs  

## Exceptions & Edge Cases
- **Binary Files** — Must not be patched; only metadata may be read.  
- **Large Repositories** — Directory scans may require streaming.  
- **Symlinks** — Must not allow traversal outside repository root.  
- **Detached HEAD State** — Agent must not commit unless explicitly authorised.

## Change Control
- All changes require version increments.  
- Proposed updates must include:  
  - rationale  
  - diff summary  
  - governance impact  
  - validation plan  
- Approval authority: Systems Architect.  
- Deprecated versions must remain archived.
