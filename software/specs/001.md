## Purpose
This specification formalises the architecture and workflow required for AI agents to perform deterministic, safe, recursive directory‑level operations in a fully local environment.  
It ensures agents can read, analyse, transform, and validate entire projects while maintaining strict governance, privacy, and offline execution guarantees.

## Objectives
- Define the system components required for agentic directory operations  
- Establish deterministic workflows for multi‑step reasoning over codebases  
- Specify the filesystem tools required for safe project‑wide transformations  
- Formalise RAG integration for contextual reasoning  
- Define security, audit, and validation requirements  
- Provide implementation rules for IDE and CLI integration  

## Definitions
- **Agentic Directory Operations** — Recursive, multi‑file reasoning and transformation performed by an AI agent.  
- **OpenCode** — Local agent runtime providing multi‑step reasoning, tool execution, and project sessions.  
- **Anything LLM** — Routing and orchestration layer providing workflow triggers and RAG ingestion.  
- **llama.cpp** — Local inference runtime for lightweight conversational tasks.  
- **Unsloth Desktop** — Local fine‑tuning engine for LoRA‑based model specialisation.  
- **Codium** — IDE integration layer providing autocomplete, inline suggestions, and chat.  
- **Project Session** — Persistent agent context bound to a directory root.  
- **RAG** — Retrieval‑augmented generation using ingested project documentation.  

## Requirements

### Functional Requirements
- Agents must be able to scan directories recursively.  
- Agents must read, classify, and transform files deterministically.  
- Agents must apply patches safely using structured diffs.  
- Agents must execute scripts (linting, testing, formatting) via sandboxed tools.  
- Agents must produce structured output summarising changes.  
- All operations must be fully local and offline.

### Non‑Functional Requirements
- **Performance**: Directory scans must complete within deterministic time bounds.  
- **Reliability**: File operations must use atomic writes.  
- **Governance**: All agent actions must be logged.  
- **Security**: Tools must be sandboxed with no network access.  
- **Compliance**: All transformations must pass validation checks.

## Model / Scheme Description
The agentic directory model consists of:

### Components
- **Orchestration Layer (Anything LLM)** — Routes tasks, triggers workflows, manages RAG ingestion.  
- **Agent Runtime (OpenCode)** — Performs reasoning, executes tools, manages project sessions.  
- **Inference Runtime (llama.cpp)** — Provides fast, lightweight inference for chat and autocomplete.  
- **Fine‑Tuning Engine (Unsloth)** — Produces specialised models for project‑specific reasoning.  
- **IDE Integration (Codium)** — Provides inline agent assistance and calls local APIs.

### Relationships
- Anything LLM → routes → OpenCode  
- OpenCode → calls → filesystem tools  
- OpenCode → loads → llama.cpp models  
- Codium → invokes → Anything LLM or OpenCode  
- Unsloth → produces → fine‑tuned models → loaded into OpenCode

### Constraints
- All components must operate offline.  
- OpenCode is the only component permitted to execute filesystem actions.  
- Anything LLM must not perform destructive operations.  

## Implementation Rules

### Naming Rules
- All tools must follow snake_case naming.  
- All workflow identifiers must be deterministic and unique.

### Directory Rules
- Project root must be explicitly defined.  
- Agents may not operate outside the project root unless explicitly authorised.

### Structural Rules
OpenCode must expose the following tools:

- `scan_directory(path)`  
- `read_file(path)`  
- `write_file(path, content)`  
- `apply_patch(path, diff)`  
- `run_script(command)`

### Validation Rules
- All patches must be validated before write.  
- All script executions must be sandboxed.  
- All agent outputs must include a reasoning trace.

### Manifest Integration Rules
- Each project session must register its root path.  
- RAG ingestion must record file hashes for consistency.

## Compliance & Verification
Compliance is assessed through:

- **Automated Checks**  
  - Directory traversal correctness  
  - Patch validation  
  - Syntax validation  
  - Test execution results  

- **Manual Review**  
  - Reasoning trace inspection  
  - File modification audit  
  - Security sandbox configuration  

Required artefacts:

- Change summary  
- Modified file list  
- Execution logs  
- Validation results  

## Exceptions & Edge Cases
- **Binary Files** — Must not be modified; only metadata may be read.  
- **Large Files (>10MB)** — Must be streamed rather than fully loaded.  
- **Symlinks** — Must be resolved safely; no traversal outside project root.  
- **Generated Files** — Must be tagged to avoid recursive ingestion.

## Change Control
- All changes require version increments.  
- Proposed updates must include:  
  - rationale  
  - diff summary  
  - governance impact  
  - validation plan  
- Approval authority: Systems Architect.  
- Deprecated versions must remain archived.
